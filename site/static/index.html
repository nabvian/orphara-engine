Rare-disease decision support · open engine, written in Rust

A ranked shortlist with its reasons, and a plain statement of what is missing

Give ORPHARA a patient's reports and a short clinical note. It extracts the facts with their sources, reasons over a curated knowledge model, and hands the decision back: candidate disorders, the findings that point to each, the confirmatory tests still needed, and timing caveats. Every line traces to a source. The clinician decides.

Architecture

The engine is disease-blind; the medicine is data

No check_g6pd() anywhere, and there never will be. The engine reasons only through a frozen KnowledgeProvider contract; what each disease means lives in a compiled knowledge model. Adding a disease changes the model, never the code, which is why the engine can be open while the knowledge is still being built.

How it stays honest

Four rules the engine is built to keep

Disease-blind

The contract in core-types is frozen and standard-library only. Reasoning crates never name a disease; adding one changes the knowledge, not the code.

Nothing is guessed

A concept the model cannot place is quarantined and shown, never invented. A missing confirmatory test makes a candidate Possible, and the engine names what is missing.

Absent is not unknown

A documented absence is carried as absent; a fact nobody recorded stays unknown. Collapsing the two would manufacture false contradictions.

Rules gate; the model only ranks

Deterministic rules decide acceptance and abstention. The graph model can reorder candidates within a tier but never move one across a tier.

Outcome labels

None of these is a diagnosis. They are an ordering with the reasons attached.

Scope · from the proof to the whole inventory

Three horizons, smallest to largest

Growth is knowledge work, not engine work: the engine in this repository does not change as diseases are added.

3The proof build

Three red-cell enzyme disorders modelled end to end in the private knowledge base: real reports and a real note in, a full, sourced, structured analysis out. Three is the proof that the pipeline works, not the ambition.

230Year one: Hematology

Open now: the engine

The disease-blind reasoning core, the knowledge format and compiler, the extractor, the concept adapter, the timeline pass and a local web UI, under the GNU AGPL-3.0. Bundled with a synthetic example model so it builds, tests and demos end to end.

Open after validation: the knowledge

The sourced, reviewed disease models stay private until they are clinically validated. Publishing an unvalidated clinical knowledge base invites it to be used as if it were finished. After validation the full suite, knowledge included, will be open-sourced.

Future upgrades · the year-one milestone plan

What comes next

The plan for the coming year builds out the Hematology family, milestone by milestone, with every disorder passing the engine's confirmatory-gating and provenance checks. Taken from the project's milestone plan and README.

  1. Month 1Hematology family map and engine readiness

    Resolve the ~230 Hematology entities into families and sub-families as a published classification map, and ready the open engine and its public build and CI for group and subtype handling.

  2. Months 2–4First sub-families end to end

    Sourced dossiers and compiled models for the first sub-families, for example red-cell membrane and haemoglobin disorders, with a progress report of counts and sources.

  3. Months 5–7Coverage and differentials

    Further sub-families such as coagulation and bone-marrow failure, plus cross-disorder differential reasoning. Engine improvements released publicly.

  4. Months 8–10Toward full-family coverage

    The remaining Hematology sub-families, each disorder passing confirmatory gating and provenance checks, with cumulative coverage reported.

  5. Months 11–12Validation package

    A clinician-review package with a synthetic case suite and per-disorder review packets, a public engine release, and a written clinical-validation plan.

  6. After validationThe knowledge base opens

    Once clinically validated, the full suite, knowledge included, is open-sourced.

  7. UltimatelyEvery rare disease

    From one family to the full Orphanet inventory of 10,288 active entities, with each entity's level resolved as part of the build.

To support the work, see funding.json; the plan is milestone-based, each tranche released on a concrete deliverable.

Run it locally

Install and run

# Rust 1.80 or newer
git clone https://github.com/nabvian/orphara-engine
cd orphara-engine
cargo test --workspace
cargo run -p concept-adapter --example analyze_note
cargo run -p poc-server     # local UI on http://127.0.0.1:8794

# your own compiled model, no code change
ORPHARA_MODEL=/path/to/model.dsdsrc cargo run -p poc-server

Nothing phones home; it runs entirely on your machine. A walkthrough is in USAGE.md, and a Colab notebook runs it with nothing to install.

This page

What runs here

  • The engine crates caretrace, concept-adapter, dsd, dsdc, engine, gnn, reasoning and temporal, unmodified, compiled to one WebAssembly module behind a thin bridge in site/web.
  • The bundled synthetic example model and the synthetic documents from samples/. The private knowledge base is not on this page.
  • PDFs are read by the engine's own PDF reader. In the browser a malformed PDF cannot be caught the way the native build catches it, so the engine is restarted and the file is reported as unreadable.
